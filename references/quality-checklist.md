# AI法律解读与交付质量检查清单

## 使用方式

根据任务选择检查模块，不要求简单法律问答执行与任务无关的全部项目：

1. 所有法律解读至少执行“法律来源与效力”和“法律分析与分类”的相关项目；
2. 面向普通企业制作合规指引、FAQ或业务说明时，增加“业务转化质量”；
3. 制作Excel、多工作表清单、自查工具或结构化规则库时，增加“表格和交付质量”；
4. 用户只要求翻译、文件定性、局部条款分析或清单复核时，只执行必要模块，但不得省略控制文本、法律状态和引用核验。

发现关键来源缺失、法律状态不明、分类依据冲突或业务事实不足时，不用无条件结论掩盖缺口。记录待确认事项及重新评估条件。

## 一、法律来源与效力

### 1. 来源与文件身份

- [ ] 使用官方公报、立法机关、政府、主管机关或其他可验证权威来源；
- [ ] 已记录文件正式名称、编号、法域、发布机构和文件类型；
- [ ] 搜索摘要、新闻稿、登录页、失败下载页或仅含元数据的页面未被当作已读取正文；
- [ ] 原始文件、官方链接、查询日期和控制版本已经保留；
- [ ] 多份文件共同形成规则时，已说明上位法、实施文件、决定、附件、指南和标准分别提供什么内容；
- [ ] 法律依据与结论直接对应，没有用内部表格或二手文章替代正式来源。

### 2. 法律状态、日期与版本

- [ ] 正式法律、实施文件、授权决定、草案、征求意见稿、指南、准则、标准和新闻说明已经区分；
- [ ] 通过、签署、公布、发布、生效和开始适用日期没有混淆；
- [ ] 法律约束力、适用阶段、过渡期和存量安排已经核验；
- [ ] 分析写明截至日期并使用当时有效的控制版本；
- [ ] 修法或清单变更结论基于具体文本，并标明是否最终通过；
- [ ] 已识别文件被废止、替代、部分失效或分阶段适用的情况；
- [ ] 可能变化的法律状态在交付前重新核验。

### 3. 全文、附件与翻译完整性

- [ ] 正文、序言、定义、例外、过渡条款、附件、附表、表格、脚注和修订标记未遗漏；
- [ ] 风险清单、禁止清单、产品清单、处罚表和技术附件已经逐项覆盖；
- [ ] 交叉引用已经回查，不依据孤立条文下结论；
- [ ] PDF或OCR文本的条款编号、否定词、金额、日期、表格和专有名词已抽样核对；
- [ ] 翻译完整保留原文结构，没有总结、删减或混入法律意见；
- [ ] 术语一致，疑难术语保留原文并可以回查原文位置；
- [ ] 无法取得全文、附件、原文或最新版本时，已明确披露证据缺口及其影响。

## 二、法律分析与分类

### 1. 适用范围与法定角色

- [ ] 地域、监管对象、法定主体和时间范围均已判断；
- [ ] 已确认产品、系统、模型、功能、内容、行为或场景中哪些对象受监管；
- [ ] 公司角色按照具体系统和实际活动判断，不只依据合同名称、自研或采购标签；
- [ ] 同一组织在不同场景可能承担多个角色的情况已经处理；
- [ ] 角色定义与仅在特定风险等级或场景下触发的特殊义务没有混淆；
- [ ] 国家机关、监管机构、公共机构或特殊行业主体的专属要求未被泛化给普通企业；
- [ ] 排除、例外、豁免和特别规则已经检查；
- [ ] “不适用”结论包含业务事实、法律依据和重新评估条件；
- [ ] 信息不足时没有给出无条件的适用或不适用结论。

### 2. 禁止行为与监管分类

- [ ] 在套用角色、风险或义务模板前，已经从目标法原文识别其监管对象、主体、行为、分类方式和义务触发结构；
- [ ] 没有预设目标法一定存在“提供者／部署者”、统一风险等级、通用模型、合格评定或其他特定法域制度；
- [ ] 先检查禁止行为或不可接受实践，再判断风险等级或其他特殊类别；
- [ ] 禁止行为的主体、对象、目的、手段、影响、限定条件和例外已经完整核验；
- [ ] 定义、风险分类、特殊类别和技术门槛使用该法自身标准，没有照搬其他法域体系；
- [ ] 已识别法律分类的是系统、模型、用途、产品、决定、能力门槛还是其他对象；
- [ ] 主管机关制定或调整类别的一般标准，与企业可以直接适用的分类条件已经分开；
- [ ] 一般风险因素没有在缺乏法律授权时替代正式定义、附件或清单；
- [ ] 法定标准没有被擅自增加、删除、拆分、合并或重新命名；
- [ ] 没有使用内部评分或自创标签替代法律规定的分类机制；
- [ ] 附件或清单型分类已经逐项核验对象、用途、场景和限定条件；
- [ ] 正式清单、排除条件、官方示例和企业分类结论已经分层记录；
- [ ] 命中类别、领域或清单后，仍继续核验排除、例外或降级条件；
- [ ] 分类结论已经连接具体业务事实、公司角色和适用义务；
- [ ] 功能、用途、模型、数据、部署场景、角色、严重事件或法律变化后的重新分类条件已经列明。

### 3. 规则拆解与义务分配

- [ ] 关键条款、附件、清单和交叉引用逐项覆盖；
- [ ] 每项规则有明确主体、对象、触发条件、必须行为或禁止行为；
- [ ] 一般义务与特定角色、风险等级、模型类别或行业场景义务已经区分；
- [ ] 强制义务、条件性义务、监管解释、鼓励性要求、自愿机制和内部增强措施已经区分；
- [ ] 监管沙盒、受控试验、扶持计划或申请型机制未被写成普遍强制义务；
- [ ] 上市前、上线后、一次性、持续性和事件触发义务已经区分；
- [ ] 法定截止日和企业内部实施日期已经区分；
- [ ] 通知、登记、认证、合格评定、技术文档、日志、监测、事故报告和证据保存要求已按适用条件覆盖；
- [ ] 行业法和一般AI法律可能重复的程序已经检查衔接或等效合规规则；
- [ ] 处罚、禁用、整改、召回、赔偿和其他法律后果已经覆盖并对应正确主体。

### 4. 结论与引用

- [ ] 每个关键结论能够回溯到具体文件、条、款、项、附件或清单项目；
- [ ] 引用支持结论的全部关键限定，不存在断章取义；
- [ ] 事实、法律原文、解释性材料、分析结论和内部建议已经分层；
- [ ] 政策趋势、草案和推断没有写成现行义务；
- [ ] 争议、假设、置信度和事实缺口已经明确标识；
- [ ] 结论之间不存在角色、分类、期限或义务冲突。

## 三、业务转化质量

仅在制作面向业务人员的合规指引、FAQ、业务总表、改造清单或自查表时执行本部分。

### 1. 读者、范围与信息架构

- [ ] 已明确目标企业、目标读者、业务范围、使用目的和交付形式；
- [ ] 核心章节按照监管逻辑和业务人员需要解决的问题组织，而不是机械复制条文顺序；
- [ ] 完整法务规则底表、业务合规指引和业务自查表的用途没有混用；
- [ ] 与目标企业无关的特殊主体要求已经删除、降级到法务底表或明确标注不适用；
- [ ] 核心大类和表头在批量生成前已经确认；
- [ ] 用户已经确认的结构、表头和范围没有被擅自改变。

### 2. 业务指引内容

- [ ] “官方文件规定了什么”准确说明主体、对象、条件、义务或禁止、例外和时间；
- [ ] 业务解释没有创造法律原文之外的新义务；
- [ ] 角色章节包含必要的法定定义、业务解释和典型示例；
- [ ] 仅在特定分类下适用的角色义务放在对应分类章节，而非基础角色章节；
- [ ] 禁止行为逐项说明法律禁止什么，并提供有针对性的负面示例；
- [ ] 每个风险等级或特殊类别均说明对应角色需要完成的要求；
- [ ] 透明度、AI交互告知、内容标识和相关例外没有因跨类别适用而遗漏；
- [ ] 伦理原则、治理原则、鼓励性要求和强制义务的效力表述准确；
- [ ] 自愿或特殊机制仅在目标读者确有需要时纳入，并明确其性质；
- [ ] 没有使用“加强管理”“注意风险”等缺乏实际参考价值的笼统提示；
- [ ] 没有为了显得完整而增加无实际用途的栏目。

### 3. 清单、附件和示例

- [ ] 每个清单或附件项目保留自身对象、用途、场景和限定条件；
- [ ] 不同项目没有机械重复同一段笼统业务解释；
- [ ] 项目名称相近时已经说明区别，没有不当合并；
- [ ] 官方示例与自行编写的业务示例已经分开；
- [ ] 自行编写的示例标明“业务示例”“负面示例”或“非官方示例”；
- [ ] 示例与具体规则直接对应，没有扩大或缩小法律范围；
- [ ] 必要时同时提供命中示例和边界示例；
- [ ] 示例没有被写成唯一适用场景或正式法律条件。

### 4. 业务自查表

- [ ] 每个问题都能由业务人员依据产品、功能、用途、用户、数据、部署或运营事实回答；
- [ ] 自查题没有直接要求业务人员解释抽象法律概念；
- [ ] 复杂定义拆成事实问题时，没有改变法定条件的组合关系；
- [ ] 一般标准、正式清单、排除情形和最终结论分区呈现；
- [ ] 答案连接明确的分类结果、义务章节、后续动作或法务升级路径；
- [ ] 允许“不确定”“待确认”或法务复核，不强制生成无条件结论；
- [ ] 禁止行为、高风险或其他特殊类别、重大修改和结论冲突已经设置升级条件；
- [ ] 自查表明确属于初筛工具，没有替代必须进行的正式评定、认证或主管机关决定。

### 5. 业务改造与执行

- [ ] 业务按照产品、功能和使用场景盘点；
- [ ] 模型来源、端云位置、开发运营更新主体和目标市场已经确认；
- [ ] 每项适用义务已经连接受影响业务；
- [ ] 改造动作具体到产品、交互、研发、测试、运营、法律文件或程序；
- [ ] 每项行动有责任团队、期限、依赖项、验收标准和证据；
- [ ] 法律明确要求、为满足法律通常需要的实施动作和企业自愿增强措施已经区分；
- [ ] 高风险、不确定或跨部门事项有明确法务升级路径。

## 四、表格和交付质量

仅在交付物包含Excel、多工作表清单、业务自查工具或其他结构化表格时执行本部分，并同时遵循适用的电子表格技能。

### 1. 工作表功能与跨表一致性

- [ ] 每张工作表的目标读者和功能明确，不存在重复承担同一功能的表；
- [ ] 法务规则底表、业务合规指引和业务自查表保持用途分离；
- [ ] 使用说明和目录主要介绍核心总表内容及自查工具使用方法，没有重复完整义务；
- [ ] 目录标题与核心业务总表大类逐字一致；
- [ ] 核心总表大类稳定后才生成目录和自查导航；
- [ ] 自查问题能够对应法律条件、清单项目或稳定规则编号；
- [ ] 自查结论能够指向核心总表章节、义务集合或法务复核；
- [ ] 业务总表能够回查法务底表和法律依据；
- [ ] 修改某张表时，确需联动更新的工作表已经识别并在授权范围内处理。

### 2. 表格结构与内容呈现

- [ ] 相同大类连续出现时已经采用适当的合并或其他展示方式，避免逐行机械重复；
- [ ] 合并单元格没有破坏筛选、公式、引用或后续维护；
- [ ] 表头、编号、章节名称和引用保持一致；
- [ ] 用户输入、下拉选项、自动结果和提示区域容易区分；
- [ ] 没有无内容的空白工作表、无用途栏目或过度格式化区域；
- [ ] 长文本完整显示，没有截断关键条件、例外或法律依据；
- [ ] 颜色、边框、冻结窗格和行列尺寸服务于可读性，不只是装饰。

### 3. 公式、数据验证与结果

- [ ] 公式引用范围正确，不存在错行、漏行、循环引用或错误的跨表引用；
- [ ] 没有`#REF!`、`#DIV/0!`、`#VALUE!`、`#NAME?`或其他明显错误；
- [ ] 数据验证和下拉选项覆盖正确的可编辑区域；
- [ ] 条件格式与公式结果一致；
- [ ] 结果由用户输入决定时使用可审计公式，没有硬编码重复结论；
- [ ] 公式允许“不确定”或法务复核路径，不强制给出虚假确定性；
- [ ] 修改结构后已经重新检查公式、验证、条件格式和引用范围。

### 4. 文件版本与最终验证

- [ ] 修改基于用户最近版本，没有退回旧版本；
- [ ] 用户已有内容和修改均已保留，除非用户明确要求删除；
- [ ] 未直接覆盖成品文件，并按照当前项目或用户指定规则另存；
- [ ] 文件名只遵循当前有效命名规则，没有累加已废止的历史规则；
- [ ] 已检查关键单元格的值、公式和跨表关系；
- [ ] 已渲染并检查相关工作表或修改区域的视觉效果；
- [ ] 最终文件可以正常打开，重要内容、提示和结果清晰可见。

## 五、最终发布门槛

- [ ] 已明确本次实际执行了哪些检查模块；
- [ ] 关键来源、法律状态、适用性、角色和分类结论均有依据；
- [ ] 强制义务、鼓励性要求、自愿机制和内部建议没有混淆；
- [ ] 对事实不足、证据缺口、争议和推断进行了披露；
- [ ] 输出层级与目标读者匹配；
- [ ] 法律结论与业务指引、自查表或工作簿结果不存在实质冲突；
- [ ] 所有关键问题已经解决，或者明确列入待确认事项和后续复核路径。
