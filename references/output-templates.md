# 输出模板

## 使用原则

先根据目标读者和交付目的选择输出类型，再确定表头和内容粒度。不得把法务规则底表直接当作业务合规指引，也不得把完整法律说明原样塞入业务自查表。

制作大型表格或多工作表成果时，应先向用户确认表格类型、功能边界、章节大类和表头，再批量生成内容。用户已经确认表头或结构的，后续应保持一致，除非用户明确要求调整。

本文件提供推荐结构，不要求所有法域、法律或项目机械采用相同表头。法律自身的角色、分类和义务体系以及用户指定的模板优先。

## 表格类型选择

核心表格分为三类：

| 表格类型 | 主要读者 | 核心用途 | 内容特点 |
|---|---|---|---|
| 法务规则底表 | 法务、合规及审计人员 | 完整拆解法律规则并保留可追溯依据 | 字段完整、规则原子化、记录主体、触发条件、例外、期限、证据和后果 |
| 业务合规指引 | 产品、研发、运营、采购、销售及管理人员 | 清晰说明与普通企业业务相关的法律要求 | 按业务问题组织，语言简洁准确，配套边界解释和示例 |
| 业务自查表 | 立项、开发、采购、上线和运营环节的业务人员 | 通过业务事实初步判断适用范围、角色、分类和下一步 | 使用可回答的问题、标准化选项、结果提示和法务升级条件 |

三类表格相互关联但不能互相替代：

- 法务规则底表是详细法律分析和追溯基础；
- 业务合规指引从已核验的规则中提炼业务需要了解的内容；
- 业务自查表将适用性、角色、分类和关键义务转化为事实问题；
- 一项法律规则可以对应多项业务说明或自查问题，不要求机械一一对应；
- 业务指引和自查表不得引入法务规则底表中没有依据的新义务。

## 法务规则底表

法务规则底表追求法律覆盖、原子化和可追溯性。它可以包含业务人员不需要直接阅读的专业字段，不应因业务总表追求简洁而删减必要的法律分析。

| 字段 | 填写要求 |
|---|---|
| 内部规则编号 | 唯一且稳定 |
| 法律依据 | 文件、条、款、项、附件和原文定位 |
| 法律状态 | 现行、待适用、草案、指南等 |
| 义务主体 | 法定角色，不只写公司名称 |
| 监管对象 | 产品、系统、模型、内容、行为或场景 |
| 触发条件 | 规则适用所需的法律条件和业务事实 |
| 必须行为 | 使用可验证的动作表述 |
| 禁止行为 | 明确红线 |
| 例外或豁免 | 条件及证明责任 |
| 时间属性 | 上市前、上市后、持续性、事件触发 |
| 截止日期 | 法定日期和内部日期分列 |
| 证据 | 文档、日志、测试、审批、记录或声明 |
| 主管机关 | 监管、认证或报告对象 |
| 法律后果 | 罚款、禁售、召回、整改、责任等 |
| 配套解释 | 指南、准则、标准及其效力 |
| 待确认事项 | 法律或事实缺口 |

拆解规则时应区分强制义务、条件性义务、监管解释、鼓励性要求、自愿机制和内部增强措施。特殊主体或特殊场景的要求不得泛化适用于普通企业。

## 适用性意见

1. 结论及置信度；
2. 作为判断基础的业务事实；
3. 地域、对象、主体和时间连接点；
4. 公司角色；
5. 分类或风险等级；
6. 排除、例外和豁免；
7. 适用义务集合；
8. 不适用义务及理由；
9. 尚需确认的关键事实；
10. 重新评估触发条件。

## 业务合规指引

业务合规指引面向普通企业人员，重点是准确、清晰和便于查阅。章节大类应根据法律的监管逻辑和业务人员需要解决的问题提炼，不应机械复制法律条文顺序。

### 推荐表头

| 大类 | 具体事项 | 官方文件规定了什么 | 业务解释／示例 | 法律依据 |
|---|---|---|---|---|

该五列表头是推荐模板。用户另有模板或者特定项目需要增加状态、责任团队、适用场景等字段时，以用户确认的结构为准。

### 各列填写要求

- **大类：**对应稳定的业务问题或监管主题，例如适用范围、法定角色、禁止行为、监管分类、透明度、责任。大类应先稳定，再用于目录或其他工作表；同一大类连续出现时可在展示层合并单元格，不逐行重复堆叠。
- **具体事项：**用简洁名称标识单项定义、禁止行为、分类条件、义务、例外或责任，不使用不能区分内容的泛化标题。
- **官方文件规定了什么：**准确汇总法律、实施文件、附件和主管机关决定中的直接要求。应写清主体、对象、条件、行为和例外；不得混入内部建议，也不得将鼓励性要求写成强制义务。
- **业务解释／示例：**解释适用边界、条件、例外和典型场景。示例应与具体规则对应，并标明“业务示例”“负面示例”或“非官方示例”；不得扩大或缩小官方规则范围。
- **法律依据：**精确到文件、条、款、项、附件或清单项目。多份文件共同形成一项要求时，应列明各自作用。

### 内容组织要求

- 角色章节应说明法定角色名称、官方定义、必要的业务解释和示例；仅在特定风险等级或场景下触发的特殊义务，应放入相应风险或场景章节。
- 禁止行为应逐项说明法律禁止什么、构成条件或边界，并提供有针对性的负面示例。
- 法律采用风险等级、特殊类别、法定领域、附件清单或其他分类机制时，应分别说明判断条件、排除情形和分类结果对应的义务，不得擅自拆分或增加法定标准。
- 不同风险等级的专属义务原则上与相应等级放在一起；透明度、内容标识等跨类别义务可以根据法律结构单独成章。
- 对清单或附件逐项说明时，每个项目应保留自身的对象、用途、场景和限定条件，不得用同一段笼统解释替代不同项目的实质内容。
- 受控试验、监管沙盒、扶持政策等自愿或申请型机制，只有在目标读者需要了解时才纳入，并明确其不是普遍强制义务。

## 完整合规指引

### 一、执行摘要

- 文件性质和状态；
- 生效和适用时间；
- 核心监管制度；
- 公司总体适用性；
- 受影响业务；
- 高优先级行动和主要法律后果。

### 二、监管框架与适用性

- 定义；
- 地域和对象范围；
- 角色；
- 分类决策树；
- 排除、例外和过渡安排。

### 三、详细义务与改造

每项按“依据—主体—对象—触发条件—义务/禁止—例外—业务影响—改造—期限—证据—处罚”展开。

### 四、实施路线图

按法律截止日倒排法务判断、产品方案、开发、测试、供应商协同、认证或备案及正式发布。

### 五、法律依据

分列现行法律、实施文件、正式指南、行为准则、标准、审议文件和辅助说明，并标记法律状态和查询日期。

## 业务自查表

业务自查表用于初步识别适用性、法定角色、监管分类、禁止性场景和关键程序要求。根据任务复杂度，可以将角色与适用范围自查、风险分类自查或其他专项自查分别设置，不要求全部放入一张表。

### 推荐表头

| 编号 | 判断主题／领域 | 业务事实问题或清单项目 | 选择答案 | 业务补充说明 | 判断结果／下一步 | 依据提示 |
|---|---|---|---|---|---|---|

### 编写要求

- 问题必须由业务人员依据产品、功能、用途、用户、数据、部署和运营事实回答，避免直接要求其解释抽象法律概念；
- 对复杂定义可以拆成多个事实问题，但不得把一个法定标准误拆成多个彼此独立的法律条件；
- 答案应连接到明确的分类结果、适用义务、后续章节或法务升级路径；
- 选择项应根据问题设计，可以包括“是／否／不确定”“命中／未命中／待确认”等，不强制所有问题使用同一选项；
- 允许填写补充事实和证据来源；
- 对禁止性场景、高风险或其他特殊类别、角色变化、重大修改和程序性义务设置升级条件；
- 一般标准、官方清单、法定定义、排除情形和最终结论应分层呈现，不能用内部评分替代法律规定的分类机制；
- 在立项、模型开发或引入、上线、重大变更、新地区发布等适当节点触发重新自查；
- 自查表只支持初步判断。法律标准复杂、事实不足、结论冲突或者风险显著时，应提交法务复核。
